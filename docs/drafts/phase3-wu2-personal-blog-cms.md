# 一个个人博客 CMS 如何从 UI 壳层走向可运营系统

> 状态：Draft · 阶段三 WU2
> 本文只用于内部审核，不自动发布。

很多个人博客一开始并不缺页面。

缺的是页面背后的“继续维护”这件事。

我最初面对 Yu-log 时，手里更像是一组已经有视觉方向的静态 UI：有首页，有文章页，有项目展示，也有一套比较完整的 Cybernetic Garden 语言。但这些页面还不能回答几个很实际的问题：文章保存在哪里？项目详情怎么维护？笔记和时间线是不是也要成为内容？留言和评论出现以后，谁来处理它们？

所以，这次工作的重点不是再画一张更漂亮的首页，而是让 UI 壳层逐步接上一个真实的内容系统。

## 从静态页面开始，先确认“什么值得被保存”

如果只把博客理解成文章表，模型很快就会变得别扭。

Yu-log 的初始 schema 里，除了 `article`，还包括 `project`、`note`、`timeline_event`、`comment`、`message`、`site_setting` 和 `operation_log` 等边界。这个结构让我重新意识到：个人博客不只是发布文章的地方，也可以是项目档案、学习记录、成长节点和互动入口的集合。

这并不意味着一开始就要把所有功能做得很重。更实际的做法，是先把内容单元分清楚：

- 文章承载相对完整的工程文章，包含 Markdown 正文、摘要、状态、发布时间和阅读信息。
- 项目承载作品与实践，除了简介，还有详情、技术栈、可见性和排序。
- 笔记承载更轻量的知识记录，有主题、标签和公开状态。
- 时间线承载节点，有日期、类型、摘要，以及和文章或项目的关联。

页面因此不再只是“把数据摆出来”。每一种内容都有自己的展示方式，也有自己的管理入口。

## 后端骨架的意义：让内容有地方落脚

Yu-log 的后端使用 Java 21 和 Spring Boot 3，数据访问使用 MyBatis-Plus，MySQL 8 负责主要内容存储，Redis 参与缓存和计数相关工作；认证侧使用 Spring Security 和 JWT。前端则是 Vue 3、TypeScript、Vite、Vue Router、Pinia、Axios 和 Tailwind CSS。

这段技术栈本身并不特别。真正改变项目状态的，是它把前端的展示对象变成了后端能够持续读写的对象。

公开接口提供首页概览、文章、项目、笔记、时间线、关于我和留言等读取入口。Admin 接口则覆盖文章、分类、标签、项目、笔记、时间线、评论、留言、站点配置和文件上传。前端 Router 对公开路由和受保护的 Admin 路由做了明确分隔，Admin 还需要认证和管理员权限。

这让“页面完成”有了另一个判断标准：不是截图看起来完整，而是页面中的内容可以从真实接口读取，并且有对应的维护路径。

## 数据库迁移记录了系统如何变复杂

一个个人项目很容易在第一版 schema 里过度设计，也很容易在需求出现以后直接改表、改代码，然后忘记自己改过什么。

Yu-log 使用 Flyway 管理迁移。V1 先建立基础表结构和文章搜索字段；之后，V3 补充文章阅读时间，V4 扩展评论和留言的回复字段，V5 给项目、笔记、时间线和站点配置补充详情、主题、标签、可见性与分组等内容元数据，V6 为文章查询条件补充索引检查和创建逻辑，V7 增加管理员需要改密的安全字段。

这些迁移并不是一个“从零一次设计完”的故事。它更像是系统在真实使用过程中，不断暴露新的内容边界，然后把边界写回模型。

对个人项目来说，这种渐进式演进有一个好处：每一次变化都留下了记录。未来回头看时，可以知道某个字段为什么出现，也能更容易区分“当时必须解决的问题”和“后来才变重要的能力”。

当然，迁移文件能证明的是 schema 如何变化，不能自动证明所有生产迁移都已经演练完毕。因此，我会把它称为“可追踪的演进”，不会把它写成“已经具备无风险上线能力”。

## CMS 不只是一个编辑器

当文章、项目、笔记和时间线都进入系统后，Admin 的职责也发生了变化。

它不只是一个输入框加一个保存按钮，而是一个小型的内容工作台：需要区分草稿和公开状态，需要预览 Markdown，需要维护分类与标签，需要处理评论和留言，还要有站点配置、文件上传和账号安全入口。

在前端体验上，Markdown 编辑器使用和公开端共享的渲染器，并提供编辑、分栏和预览模式。本地草稿会自动保存，离开有未保存修改的页面时会给出保护提示。这个能力没有改变文章的业务数据结构，却让“写作过程”更接近一个可以长期使用的工具。

这里有一个很容易被忽略的区别：本地草稿是浏览器侧的恢复机制，服务器上的草稿保存和发布仍然是另一条链路。两者分开，才能避免一次刷新或一次误操作覆盖服务器内容。

## 真实数据让页面开始承担责任

接上真实 API 以后，页面不再可以随意使用占位内容。首页的 Hero、统计、当前学习内容、最新文章、精选项目、笔记和时间线都来自接口；文章列表需要处理搜索、分类、标签和排序；项目页需要处理状态和技术栈；笔记与时间线要处理自己的主题、类型和筛选。

这会带来一些不那么“好看”的现实问题：有些内容还没有封面，有些项目的详情不完整，有些数据库里留着阶段验证记录，有些资源路径可能已经失效。

但这正是从 UI 壳层走向可运营系统的分界线。系统需要对不完整内容有安全回退，需要把测试记录和正式内容区分开，也需要在没有数据时给用户一个清楚的空状态，而不是把所有问题藏在假数据后面。

截至 2026-09-02 的本地运行时快照，公开接口可以读到 3 条文章记录、2 个项目、4 条笔记和 5 条成长记录。这个数字只是当前开发环境的快照，其中存在阶段验证遗留记录，不能当成正式内容规模，也不能推导访问量、活跃用户或线上运营结果。

## “可运营”到底意味着什么

在这篇文章里，“可运营”不是一个夸张的上线宣言。

它更接近几个具体能力的组合：

1. 内容有清晰的模型，不需要把所有东西都当成文章。
2. 公开端从真实 API 读取内容，页面不依赖静态占位数据。
3. Admin 有对应的维护入口，可以保存草稿、预览、管理状态和处理互动。
4. 数据库结构通过迁移文件演进，而不是只存在于某次本地修改里。
5. 不完整内容、失效资源和空结果有明确的回退与提示。
6. 认证、管理员权限和账号安全被当作系统边界，而不是最后才补的一层页面。

这些能力仍然不等于生产系统的全部要求。部署、备份恢复、媒体完整性、监控、限流、审计和安全演练仍然需要独立验证。但至少，项目已经从“页面可以展示什么”开始转向“内容如何持续存在、被维护并对外呈现”。

## 回头看，最重要的变化不是技术栈

从 Stitch 静态 UI 到 Vue 页面，再到 Spring Boot、MySQL、Redis 和 Admin 内容工作台，表面上看是技术栈越来越完整。

但真正重要的变化，是我开始把博客当成一个需要长期照看的系统。

首页不是一次性交付的海报，文章不是写完就结束的 Markdown 文件，项目也不是一张永远不会变化的卡片。它们都有状态、边界、维护动作和失败情况。

当这些事情被写进数据模型、迁移记录、接口和管理页面以后，个人博客才开始拥有“长期运营”的可能性。

下一步仍然不是马上发布更多内容，而是继续把事实、脱敏和审核流程做扎实。对于个人系统来说，能留下来的内容，通常比一次性完成的页面更重要。
